# USFR 视频复刻服务中文部署配置手册

本文用于把 `universal-source-fidelity-replication` 部署成独立的 Python 视频服务。部署人员只需要解压服务包、填写一个 `.env` 文件，再使用 Docker Compose 启动。

本服务只负责视频复刻能力，不包含用户账号、会员、计费、订单、前端页面、长期项目历史和运营后台。

## 1. 先看结论

- 部署方式：Python 服务 + Docker Compose。
- 内置组件：API、Worker、Sweeper、Redis、MinIO、MinIO 初始化器。
- 外部能力：GPT API、RunningHub 工作流 API、RunningHub Seedance 标准模型 API。
- 输入要求：爆款原视频必传，最长 30 秒；还要至少提供一个替换素材、上传音乐或输出语言。
- 用户确认：正常生成路线只允许确认文字脚本和故事板；纯语言替换路线按当前 Skill 契约自动执行，不等待这两次确认。
- 数据保存：长期只保留最终视频 `final/{job_id}/result.mp4`，上传文件、中间图、中间音频、故事板、Provider 视频和 Redis 任务状态均为临时数据。
- 初次部署必须保持 `USFR_PROFILE_MODE=shadow`。不要未经真实质量验收直接改成 `active` 或 `production`。

## 3. 服务器准备

建议使用 Linux 服务器，提前安装：

- Docker Engine；
- Docker Compose v2，即可以执行 `docker compose`；
- 至少 20 GB 可用磁盘，批量并发时按素材量增加；
- 可以访问 OpenAI 和 RunningHub HTTPS 接口的网络；
- 对外只需开放 USFR API 端口。MinIO 控制台不要直接暴露到公网。

视频生成主要在云端完成，本机主要负责 FFmpeg 分析、切片、合成、质检、Redis 队列和 MinIO 存储。并发量越大，CPU、内存、磁盘读写和出口带宽要求越高。

## 4. 最快部署步骤

以下命令都在解压后的工程根目录执行。

### 第一步：创建配置文件

```bash
cp .env.example .env
```

然后编辑 `.env`，不要把真实 API Key 写进镜像、代码或 Git。

### 第二步：至少填完这些必填项

```dotenv
USFR_CAPABILITY_SECRET=请填写至少32字节的随机字符串
USFR_DEPLOYMENT_FACTORY=server.packaged_factory:build_runtime
USFR_PORT_FACTORY=server.packaged_ports:build_ports
USFR_PROFILE_MODE=shadow
USFR_API_PORT=8080

USFR_S3_BUCKET=usfr-media
AWS_ACCESS_KEY_ID=请修改MinIO用户名
AWS_SECRET_ACCESS_KEY=请修改MinIO强密码
AWS_DEFAULT_REGION=us-east-1

OPENAI_API_KEY=请填写
OPENAI_BASE_URL=https://api.openai.com/v1
OPENAI_MODEL=请填写实际使用的GPT模型名
OPENAI_MODEL_CONFIG_SHA256=请填写64位小写SHA256

RUNNINGHUB_API_KEY=请填写工作流API密钥
RUNNINGHUB_SEEDANCE_API_KEY=请填写Seedance标准模型API密钥
RUNNINGHUB_BASE_URL=https://www.runninghub.ai
RUNNINGHUB_SEEDANCE_CREATE_URL=https://www.runninghub.ai/openapi/v2/bytedance/seedance-2.0-fast-token/multimodal-video
RUNNINGHUB_SEEDANCE_QUERY_URL=https://www.runninghub.ai/openapi/v2/query
RUNNINGHUB_SEEDANCE_UPLOAD_URL=https://www.runninghub.ai/openapi/v2/media/upload/binary
RUNNINGHUB_SEEDANCE_CONFIG_SHA256=请填写64位小写SHA256
RUNNINGHUB_WHISPER_WORKFLOW_ID=请填写当前使用的Whisper工作流ID
RUNNINGHUB_WHISPER_INPUT_NODE_ID=12
RUNNINGHUB_WHISPER_INPUT_FIELD=audio
SEEDANCE_API_PROVIDER=runninghub_standard
```

### 第三步：检查 Compose 配置

```bash
docker compose -f deployment/docker-compose.yml config
```

如果这里报错，先修复 `.env`，不要继续启动。

### 第四步：构建并启动

```bash
docker compose -f deployment/docker-compose.yml up -d --build
```

### 第五步：查看状态

```bash
docker compose -f deployment/docker-compose.yml ps
docker compose -f deployment/docker-compose.yml logs --tail=200 api worker sweeper
```

### 第六步：检查服务

```bash
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
```

- `/healthz` 返回成功：只代表 API 进程活着。
- `/readyz` 返回 `ready`：代表 Redis、MinIO、Skill 包、模型能力和 Provider 配置都通过启动检查。
- `/readyz` 不是 200 时，不要提交真实付费视频任务。

## 5. `.env` 配置说明

### 5.1 服务基础配置

| 配置项 | 怎么填 | 作用 |
| --- | --- | --- |
| `USFR_CAPABILITY_SECRET` | 至少 32 个 UTF-8 字节的随机字符串 | 为每个任务签发临时访问令牌，必须保密 |
| `USFR_DEPLOYMENT_FACTORY` | 保持 `server.packaged_factory:build_runtime` | 创建 API、Worker、Redis、MinIO 和清理器 |
| `USFR_PORT_FACTORY` | 保持 `server.packaged_ports:build_ports` | 加载本包内的 GPT、RunningHub、FFmpeg 等能力 |
| `USFR_PROFILE_MODE` | 初次必须为 `shadow` | 功能验证模式；生产模式有更严格的证据和质检要求 |
| `USFR_API_PORT` | 默认 `8080` | 服务器对外 API 端口 |

生成随机密钥示例：

```bash
openssl rand -hex 32
```

PowerShell 示例：

```powershell
-join ((1..64) | ForEach-Object { '{0:x}' -f (Get-Random -Maximum 16) })
```

### 5.2 MinIO 配置

| 配置项 | 怎么填 | 作用 |
| --- | --- | --- |
| `USFR_S3_BUCKET` | 默认 `usfr-media` | 存储素材和最终视频的私有 Bucket |
| `AWS_ACCESS_KEY_ID` | 自定义，不要继续用 `minioadmin` | MinIO 管理账号 |
| `AWS_SECRET_ACCESS_KEY` | 使用强密码 | MinIO 管理密码 |
| `AWS_DEFAULT_REGION` | 默认 `us-east-1` | S3 客户端区域名 |

Compose 内部会自动使用：

```text
USFR_S3_ENDPOINT=http://minio:9000
```

MinIO 地址：

- S3 接口：`http://服务器IP:9000`
- 管理控制台：`http://服务器IP:9001`

生产环境建议通过防火墙关闭公网对 9000 和 9001 的直接访问，只允许内部服务访问。

重要：当前包内的 `docker-compose.yml` 没有给 MinIO `/data` 声明持久卷。功能测试可以直接启动，但长期部署前必须补上持久卷，否则删除或重建 MinIO 容器时，最终视频也会一起丢失。建议在 Compose 中加入：

```yaml
services:
  minio:
    volumes:
      - usfr-minio-data:/data

volumes:
  usfr-minio-data:
```

### 5.3 OpenAI 配置

| 配置项 | 怎么填 | 作用 |
| --- | --- | --- |
| `OPENAI_API_KEY` | 服务端密钥 | 所有语义推理、脚本、故事板规划和卖点分析 |
| `OPENAI_BASE_URL` | 官方默认 `https://api.openai.com/v1` | OpenAI API 地址，必须是 HTTPS |
| `OPENAI_MODEL` | 填实际启用的模型名 | 固定当前部署使用的 GPT 模型 |
| `OPENAI_MODEL_CONFIG_SHA256` | 64 位小写 SHA256 | 标记当前模型和配置版本，防止任务中途换配置 |

生成配置摘要的简单方式：

```bash
printf '%s' 'provider=openai;model=你的模型名;base_url=https://api.openai.com/v1;config=v1' | sha256sum
```

只把输出的 64 位摘要填入 `.env`，不要把 API Key 放进摘要原文。

### 5.4 RunningHub 配置

| 配置项 | 怎么填 | 作用 |
| --- | --- | --- |
| `RUNNINGHUB_API_KEY` | 普通工作流 Key | 文件上传、Whisper、故事板 Image2 |
| `RUNNINGHUB_SEEDANCE_API_KEY` | Seedance 标准模型 Key | 最终视频生成 |
| `RUNNINGHUB_BASE_URL` | `https://www.runninghub.ai` | 普通工作流基础地址 |
| `RUNNINGHUB_SEEDANCE_CREATE_URL` | 保持示例值 | 创建 Seedance 2.0 fast-token 视频任务 |
| `RUNNINGHUB_SEEDANCE_QUERY_URL` | 保持示例值 | 查询任务状态和任务 ID |
| `RUNNINGHUB_SEEDANCE_UPLOAD_URL` | 保持示例值 | 上传 Seedance 参考图、参考视频片段和音频片段 |
| `RUNNINGHUB_SEEDANCE_CONFIG_SHA256` | 64 位小写 SHA256 | 固定 Seedance 模型和端点配置版本 |
| `RUNNINGHUB_WHISPER_WORKFLOW_ID` | 填当前已验证的工作流 ID | 把音频转成带时间戳文字；符合演唱条件时也用于提取上传歌曲歌词 |
| `RUNNINGHUB_WHISPER_INPUT_NODE_ID` | 固定 `12` | Whisper 工作流的音频输入节点 |
| `RUNNINGHUB_WHISPER_INPUT_FIELD` | 固定 `audio` | 节点输入字段名 |

Seedance 配置摘要示例：

```bash
printf '%s' 'provider=runninghub;model=seedance-2.0-fast-token;resolution=720p;ratio=9:16;config=v1' | sha256sum
```

注意：两个 RunningHub Key 可以来自同一账号，但不要默认它们权限相同。必须分别验证普通工作流和标准模型接口。

## 6. Docker Compose 架构

```text
客户端或业务后端
        |
        v
API :8080  ---- Redis ---- Worker ---- GPT / RunningHub
   |                         |
   |                         v
   +------ MinIO <------ FFmpeg 合成与质检
              |
              v
     final/{job_id}/result.mp4

Sweeper 定时清理 Redis、uploads/ 和 temporary/
```

| 服务 | 做什么 | 是否长期保存数据 |
| --- | --- | --- |
| `api` | 创建任务、查询状态、修改和确认脚本/故事板、获取最终结果 | 否 |
| `worker` | 执行完整视频复刻链路 | 否 |
| `sweeper` | 删除过期任务和所有临时文件 | 否 |
| `redis` | 保存临时任务状态、版本、审批、队列和 Provider task ID | 否，Compose 关闭了持久化 |
| `minio` | 保存上传素材、中间产物和最终 MP4 | 只长期保留最终 MP4 |
| `minio-init` | 启动时创建私有 Bucket | 执行完退出 |
| `e2e` | 仅用于容器流程测试 | 正常部署不启动 |

API、Worker、Sweeper 使用同一个镜像，只是启动角色不同，因此功能版本不会出现 API 新、Worker 旧的问题。

## 7. 用户可以提供的素材

七个固定入口：

| 入口 | 是否必传 | 用途 |
| --- | --- | --- |
| `source_video` | 必传 | 爆款原视频，最长 30 秒 |
| `new_product_image` | 可选 | 替换实物商品或产品视觉 |
| `new_model_image` | 可选 | 替换人物、模特身份 |
| `ui_screenshot` | 可选 | 提供需要重建的新 App UI 真值 |
| `app_store_url` | 可选 | 提取官方 App 名称、图标和商店截图 |
| `ui_operation_video` | 可选 | 直接替换原视频 UI 操作片段，不重画内容 |
| `tail_video` | 可选 | 替换原视频尾部 App 页面或尾卡 |

两个附加参数：

| 参数 | 用途 |
| --- | --- |
| `background_music` | 上传新音乐或歌曲，不算第八个固定入口 |
| `output_language` | 选择 `en/ja/ko/fr/de/es/pt/id/zh`，默认必须为空，不能自动选中文 |

合法输入条件：

```text
有效 source_video
并且
至少一个替换入口、background_music 或 output_language 有效
```

只有原视频、没有任何修改目标时，任务会在分析和付费调用之前被拒绝。

## 8. 不同素材如何路由

系统先绑定用户明确上传的入口，再根据需要选择最少的工具。禁止一开始对所有路线做全量深度分析。

| 用户提供的内容 | 实际路线 |
| --- | --- |
| 商品图 | 只重做真正受商品替换影响的镜头，其他镜头尽量保留原片 |
| 模特图 | 对受影响镜头启用人物一致性和表演复刻，不重做无关 UI/尾部 |
| UI 截图 | 进入 `generated_ui_demo`，先冻结文字和布局，再生成确定性 UI 视频并做 OCR/布局检查 |
| App Store 链接 | 只有确认需要生成 UI 时才解析一次官方商店证据；纯本地拼接或已有 UI 操作视频时跳过解析 |
| UI 操作视频 | 进入 `opaque_ui_demo`，只做黑边裁切、画幅规范、转场和时间轴拼接，不做 OCR、语义分析或重画 |
| 尾部视频 | 删除原尾卡，按上传视频自然时长拼接；不循环、不补黑帧、不拉伸 |
| 没有尾部视频 | 删除原视频识别出的尾卡，结束在前一个有效画面 |
| 只改语言 | 保留人物、商品、UI、镜头和节奏，只替换语言、可见文字和相关音频；按当前契约自动执行，不等待脚本和故事板确认 |
| 上传音乐，原视频不是明确 MV 演唱 | 只替换背景音乐，不生成歌词口型 |
| 上传音乐，原视频是明确的镜头内演唱 | 提取上传歌曲歌词，绑定演唱人物和时间窗，Prompt 使用 `@Audio1`、精确人物 ID 和歌词，再进入演唱/口型路线 |

上传音乐的 MV 判断是轻量判断：只有原分析已经确认该时间窗是 `sung`、演唱者在镜头内、人物身份已确认，并且内容和人物置信度都不低于 0.80，才允许人物唱歌。无法确认时自动降级为纯 BGM 替换，避免错误人物唱歌和额外推理。

最终语言口型和确认后的演唱口型使用固定 RunningHub 工作流合同：

```text
workflow_id = 2080140197518823426
音频输入节点 = 3
视频输入节点 = 6
```

该工作流输出的视频已经带有对应音频，后续禁止再混入另一条不同音轨。

## 9. 从开始到结束的功能链路

整套流程保持 12 个语义阶段：

1. 绑定输入：检查七个入口、音乐、语言、文件哈希和原视频时长。
2. 建立目标真值：记录新商品、新人物、新 UI 和 App 证据。
3. 拆解原视频：从第 0 帧到结束分析镜头、动作、运镜、文字、对白、音乐、音效和静音区间。
4. 路由区域：区分需要生成、保留原片、替换 UI、替换尾部或删除尾卡的区间。
5. 卖点分析：拆解原视频卖点，再用新商品或 App 的有效证据替换，禁止编造卖点。
6. 生成文字脚本：保留原镜头时间、动作、节奏和表达功能，等待用户修改和确认。
7. 规划生成片段：只规划受替换影响的连续片段，最多 2 个 Seedance 任务，每段 4–15 秒。
8. 生成故事板：生成真实故事板 PNG，等待用户修改和确认。
9. 编译和内部审核：由 Seedance-20 把已确认脚本、故事板、人物、商品、精确台词和音频时间窗编译成最终请求。
10. RunningHub 生成：上传当前任务所需素材，创建 Seedance task ID，查询并下载成功视频。
11. 时间轴合成：用 FFmpeg 拼接生成视频、保留原片、UI 操作视频、尾部视频、文字层和音频层。
12. 最终质检与发布：检查音视频流、时长、黑帧、冻结、口型、人物/商品一致性、UI 文字和时间轴，合格后发布最终 MP4。

正常复合需求，例如“改语言 + 换模特 + 换 App + 换 UI 操作 + 换尾部 + 上传音乐”，不会走六遍全流程。系统只做一次原视频分析和一次统一脚本，随后按时间区间分路处理，再统一合成。

## 10. 用户确认规则

正常生成路线最多只有两次用户确认：

1. 文字脚本确认；
2. 故事板确认。

确认故事板后，Prompt 编译、Provider 提交、等待生成、合成和 QC 都自动完成。Prompt 审核和请求摘要校验属于内部安全检查，不是第三次用户确认。

例外：

- 全部区间都能直接保留或确定性拼接时，可以不进入脚本、故事板和 Seedance。
- 只有 `output_language` 的纯语言替换，按当前顶层 Skill 契约绕过两次人工确认。
- 修改已确认脚本会使后续故事板、Prompt、Provider 和 QC 结果失效，需要重新生成并确认故事板。
- 修改已确认故事板会使后续 Prompt、Provider 和 QC 结果失效，但不要求重新确认未改变的脚本。

## 11. API 最简调用顺序

公开接口统一位于：

```text
/api/v1/jobs
```

正常顺序：

```text
1. 把文件上传到 MinIO 的 uploads/{upload_scope}/...
2. POST /api/v1/jobs
3. 保存返回的 job_id、capability_token、version
4. POST /api/v1/jobs/{job_id}/start
5. GET  /api/v1/jobs/{job_id}/scripts
6. 修改或确认脚本
7. GET  /api/v1/jobs/{job_id}/storyboards
8. 修改或确认故事板
9. GET  /api/v1/jobs/{job_id}
10. GET /api/v1/jobs/{job_id}/result
```

创建任务后返回的 `capability_token` 只显示一次。之后每个任务接口都要带：

```http
Authorization: Bearer <capability_token>
```

每次修改操作还要带当前 `expected_version`。版本过期时先重新查询任务，不要盲目重复提交。

服务 API 接受的是已经上传完成的对象记录，不是直接把 Windows 本地路径传给服务器。每个对象至少需要准确的对象键、SHA256、大小、MIME、完成状态；视频还需要真实时长。

## 12. 数据保存和自动清理

MinIO 对象规则：

```text
uploads/{upload_scope}/...        用户上传，临时
temporary/{job_id}/...           分析、故事板、音频、片段、QC，临时
final/{job_id}/result.mp4         唯一长期保存文件
```

清理规则：

- 成功任务：删除对应 uploads、temporary 和 Redis 临时状态，只保留最终 MP4。
- 失败、取消、过期任务：删除上传、中间产物和可能存在的最终文件。
- Provider 仍处于提交中、运行中或结果不明确时，不清理，以免丢失可恢复任务。
- Sweeper 只按精确 `job_id` 和 `upload_scope` 清理，禁止删除整个 `uploads/`、`temporary/` 或 `final/` 根目录。

Redis Compose 配置关闭了 RDB 和 AOF 持久化，它不是历史数据库。MinIO 是最终视频的长期存储位置，因此生产服务器必须为 MinIO `/data` 配置可靠磁盘、云盘或宿主机卷备份策略。

## 13. 常用运维命令

启动：

```bash
docker compose -f deployment/docker-compose.yml up -d
```

临时停止并保留当前容器内的数据：

```bash
docker compose -f deployment/docker-compose.yml stop
```

重新启动已停止的容器：

```bash
docker compose -f deployment/docker-compose.yml start
```

查看日志：

```bash
docker compose -f deployment/docker-compose.yml logs -f api worker sweeper
```

重建服务：

```bash
docker compose -f deployment/docker-compose.yml up -d --build
```

查看 MinIO 和 Redis：

```bash
docker compose -f deployment/docker-compose.yml logs --tail=100 minio redis
```

在没有给 MinIO 配置持久卷之前，不要执行 `docker compose down` 或删除 MinIO 容器。配置持久卷后，仍不要执行 `docker compose down -v`，除非已经确认可以删除 MinIO 中长期保存的最终视频。

## 14. 常见故障

| 现象 | 最可能原因 | 处理方式 |
| --- | --- | --- |
| Compose 提示 `USFR_CAPABILITY_SECRET` | 密钥为空或不足 32 字节 | 生成新的 64 位十六进制随机字符串 |
| `/healthz` 成功但 `/readyz` 503 | Key、模型名、SHA、Whisper 工作流、Redis 或 MinIO 未准备好 | 查看 API 和 Worker 日志中的具体 readiness 项 |
| 提示 SHA256 无效 | 配置摘要不是 64 位小写十六进制 | 重新运行 `sha256sum`，只复制摘要部分 |
| Whisper 启动失败 | 工作流 ID 为空、节点不是 12、字段不是 audio，或工作流没有返回唯一 TXT | 检查 RunningHub 工作流和节点配置 |
| 故事板没有生成 | Image2 Key、网络、参考素材或故事板范围校验失败 | 查看 `worker` 日志，不要用拼图占位绕过 |
| Seedance 没有 task ID | 标准模型 Key/端点不正确，或请求被 RunningHub 拒绝 | 保存原错误，不自动重复创建付费任务 |
| 视频等待很久 | RunningHub 正在排队或生成 | 查询已返回的 task ID，不要提交第二个任务 |
| UI 文字乱码 | 生成 UI 的文字或布局没有通过 OCR | 阻止发布；优先要求上传 `ui_operation_video` |
| UI 或尾部出现黑帧 | 活跃区间裁切、转场或 FFmpeg 时间轴失败 | 检查 splice/transition/QC 记录，不做黑帧填充 |
| 只上传音乐但人物不唱 | 原视频没有被可靠判定为镜头内演唱 | 这是安全降级，音乐只作为 BGM 替换 |
| 任务突然消失 | 临时任务 TTL 到期或 Sweeper 已清理 | 最终成功视频应仍在 `final/{job_id}/result.mp4` |

## 15. 当前版本必须知道的边界

当前打包端口可以直接连接 GPT、RunningHub Whisper、RunningHub Image2、RunningHub Seedance、Redis、MinIO 和 FFmpeg，适合本地能力迁移后的服务端功能验证和 `shadow` 模式试运行。

但是，正式商用切换到 `active/production` 前还必须完成：

- 接入并验证真正的生产 OCR / UI 视频渲染能力；
- 接入独立的语义 QC 评估器，并让结果绑定最终 MP4 的 SHA256；
- 验证语言 TTS 和固定对口型工作流的真实执行端口；当前包已经包含工作流 `2080140197518823426` 的固定请求构造器，但独立 TTS/对口型不是 `.env` 中可单独配置的 Compose 服务；
- 用真实素材完成商品、人物、App、UI、尾部、语言、音乐和复合需求的全链路测试；
- 完成业务小样测试后，再完成 36 条真实用例的发布验收；
- 验证 MinIO 持久卷、备份、HTTPS、访问控制和监控告警。

因此，第一次部署应将状态描述为：服务端视频工作流核心和外部 API 接线已经可部署验证；真实商用质量需要在 `shadow` 模式跑完实素材验收后再开放。
