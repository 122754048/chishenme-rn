# Adaptive Fidelity Recovery Loop

The recovery loop is an internal fallback inside the existing twelve-stage
workflow. It adds no public slot, semantic stage, approval, or delivery type.

## Trigger

Enter recovery immediately when the frozen goal contract requires an
undeployed capability, or when the same hard-failure signature survives two
focused standard repairs. The signature binds the failed stage, hard gate,
evidence, approved revision set, routes, timing, audio, character/product locks,
and target final-output constraints.

## Execution

The runtime may discover and use any deployed and authorized capability,
including generated one-off code, FFmpeg, Remotion, HyperFrames, Seedance,
another Provider, deterministic compositing, or a hybrid method. There is no
fixed tool whitelist, strategy list, or retry count. Generated code executes
only through the deployment sandbox and every external invocation records a
request/result receipt.

Each iteration persists a temporary Redis checkpoint containing the failure
signature, strategy, tool invocations, candidate artifact references, focused
QC delta, and next action. A strategy with no measurable improvement is not
repeated unchanged.

## Exit

A passing candidate is reinserted through the original failed stage's existing
artifact kind and must then pass the normal downstream gates. Stop only when
all hard gates pass, the user cancels, or an external authorization/provider
dependency blocks execution. Recovery checkpoints and candidates expire with
the job; only the successful final MP4 is retained.
